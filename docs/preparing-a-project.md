# Подготовить комплект одного проекта

Цель — понятный объём для независимого ответа, не демонстрация сложности. Начинайте с [методики](../methodology.md); заполненный [пример Constitution.my](../projects/constitution-my/README.md) показывает форму, но его числа и требования не переносятся в другой продукт.

## 1. Зафиксировать и заполнить

Запустите из корня репозитория:

```sh
node scripts/new-project.mjs example-project "Название проекта"
```

Замените пример реальным коротким идентификатором. Команда не перезаписывает существующую папку. Получится только черновик: README, задание с формой ответа, редакционное приложение, риски и `project.json`.

Исходники и непубличные доказательства исследуют в разрешённом рабочем окружении, вне этого репозитория. Внешний комплект получает только безопасное описание и разрешённые примеры. Не копируйте целиком рабочую папку продукта.

Заполните:

- назначение, роли, законченные сценарии и состав передачи;
- подтверждённое состояние и отдельно целевые требования, планы, исключения;
- версию основания, дату, объёмы, языки, нагрузку и единые допущения;
- W-ID с результатом, измеримым объёмом, ответственностью, зависимостями и приёмкой;
- C-ID и OP-ID: оригиналы, переводы, объёмы текста и медиа, нужные операции; отсутствие редакционного корпуса объясните, не считайте его автоматически бесплатным;
- решение по R-001–R-022, конкретные проверки применимых рисков и связанные работы;
- форму ответа по общим блокам, исключениям, налогам, срокам, правам и регулярным расходам.

Составитель заполняет свои разделы, поля ответа подрядчика остаются пустыми. Краткое задание не обязано быть длиннее самого описываемого проекта: компактная таблица допустима, если содержит необходимые сведения. При неразрешённом существенном объёме сохраняется черновик либо явно ограниченный предварительный запрос.

## 2. Проверить содержание и границы

До публикации составитель и проверяющий, если он привлечён, читают именно публикуемые файлы.

- [ ] Каждая работа нужна реальному сценарию; есть объём, единица, критерий приёмки и основание включения.
- [ ] Готовые компоненты, ИИ и пакетная автоматизация допускаются; настройка не описана как создание платформы заново.
- [ ] Общие работы, проверки, управление, импорт и редакционные операции не считаются дважды.
- [ ] Редакционные оригиналы, версии, переводы, фрагменты и экспорты разделены; нормы не выданы за замеры.
- [ ] Языковые пары, источники, права и предметная ответственность раскрыты.
- [ ] Все категории рисков рассмотрены, неприменимое исключено, меры соразмерны. ИИ-инструмент подрядчика не создаёт отсутствующего ИИ-помощника в продукте.
- [ ] Работы W-ID, риски R-ID, партии C-ID и операции OP-ID согласованы; база, замены, опции и эксплуатация разделены.
- [ ] Нет наших часов, ставок, целевой цены, реальных коммерческих ответов, закрытых ссылок, доступов и непубличных исходников.
- [ ] Неизвестное обозначено, версия зафиксирована, сведения о проверке правдивы. Самопроверка не названа независимой экспертизой.

Запустите структурные тесты:

```sh
node scripts/validate.mjs
node scripts/test.mjs
```

Структурный PASS не заполняет пункты выше и не разрешает публикацию секретных данных. Внутреннюю калькуляцию ведите отдельно, по тем же W-ID и версии задания, не в игнорируемой папке внутри публичного клона.

## 3. Зафиксировать и опубликовать

В `project.json` укажите `version`, `as_of` (дата комплекта), `source_ref` (публично разрешённое основание), `editorial` (`included` или `excluded`; для исключения нужна `editorial_note`). Приведите README к фактическому состоянию. Перечень `files` — явный разрешённый состав; `project.json` перечисляется отдельно как служебный паспорт.

Для локального заполненного комплекта после ручной проверки вычислите контрольную сумму файлов:

```sh
node scripts/validate.mjs --digest example-project
```

Запишите её в `review.manifest_sha256` вместе с `review.by`, `review.at` и `review.scope`. В `scope` укажите, что именно проверено, вид проверки и ограничения. Не записывайте имя человека, который не проверял документ. После этого можно установить `state: "published-example"` и снова проверить комплект. Это отметка о заполненном примере, не сертификат и не автоматический запуск тендера.

Добавьте карточку в список [каталога](../README.md). Сначала просмотрите `git diff` и явный список добавляемых файлов; после публикации проверьте публичную ссылку и закрепите commit для отправки. Разные подрядчики должны получить одну версию.

Необязательно заводить отдельный репозиторий для каждого нового проекта: обычное место — его папка здесь. Если публичный комплект уже живёт отдельно, как Constitution.my, сохраняйте его источником и добавляйте только закреплённый указатель. Правила структуры, внешней проверки и обновления — в [поддержании комплекта](maintaining.md).
