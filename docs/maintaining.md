# Поддержание каталога и проверка

## Где что хранится

Этот репозиторий — публичные задания и общие шаблоны. Папка `projects/<slug>` хранит один комплект или указатель на уже опубликованный комплект; она не описывает готовность всего продукта. Внутренние расчёты, коммерческие ответы и непубличные доказательства живут отдельно от публичного Git-корня. `.gitignore` не является защитой конфиденциальности.

Владелец — belilovsky. Новый общий репозиторий выбран для независимого жизненного цикла документов и возможности держать следующие комплекты в одном месте. Помещать общую методику внутрь кода одного продукта не требуется; объединять историю существующего Constitution.my тоже не требуется. Код, данные и инфраструктура продуктов не перемещаются, новых сервисов или расходов не создаётся.

Это каталог опубликованных документов, не дополнительный реестр инфраструктуры или проектов портфеля. Авторитетное содержание внешнего комплекта остаётся в его собственном репозитории. Нет утверждения, что каталог охватывает весь портфель. Решение о структуре принято для этого этапа 5 сентября 2026 года; пересматривается при реальной необходимости иной границы доступа или сопровождения.

## Статусы и версии

| `state` | Значение |
| --- | --- |
| `draft` | Задание ещё заполняется; его нельзя выдавать за готовую основу сопоставимых цен |
| `published-example` | Заполненный пример для указанного снимка; не подтверждает сегодняшний продукт, рынок или активный запрос подрядчикам |
| `needs-update` | Изменились условия предполагаемого использования; нужна новая проверка, прежний commit остаётся историей |

Перед новым запросом цен сравнить состав с текущим продуктом. Обновлять вручную при существенном изменении функций, материалов, языков, источников, требований к передаче или эксплуатации. Единого выдуманного срока годности нет. Изменение ставки во внутренней калькуляции само по себе не изменяет внешний состав.

Версии каталога, общих шаблонов и каждого проекта независимы. Исправление шаблона не меняет заполненные документы задним числом. У проекта повышают версию, записывают изменения затронутых W/R/C/OP-ID, сохраняют прежний commit. Удалённые ID не используют повторно. Изменение файлов локального примера делает старый `review.manifest_sha256` недействительным: сначала пересмотр, затем новый digest.

Если публикация содержит ошибку, исправить обычным новым commit или точечно отменить изменение. Не переписывать историю и не удалять репозиторий ради обычного исправления. Если раскрыт секрет, сначала отозвать его и ограничить дальнейшую публикацию; простое удаление строки из последнего commit не удаляет её из истории.

## Формат папки проекта

Локальный комплект содержит `project.json` и ровно `README.md`, `brief.md`, `editorial.md`, `risks.md`. При отсутствии материалов редакционное приложение сохраняет явное исключение с причиной. Если реальному продукту нужны CSV, отдельные контракты или другие приложения, расширение формата и проверки сначала делается явно; не прячьте дополнительные файлы вне перечня. Сложный готовый внешний комплект также можно подключить закреплённым указателем.

Паспорт использует `schema_version: 1`, `slug`, `name`, `state`, `version`, `as_of`, `source_ref`, `editorial`, `review`, `files`; необязательная `editorial_note` поясняет исключение. `slug` — короткое имя папки из латинских букв в нижнем регистре, цифр и дефисов. Даты записываются как `YYYY-MM-DD`. `source_ref` — разрешённое основание, не приватная ссылка и не доказательство эксплуатации само по себе.

Для локального `published-example` обязательны заполненное основание и дата, решение по материалам, отсутствие незаполненных маркеров в авторских разделах и `review` с полями `by`, `at`, `scope`, `manifest_sha256`. Это запись заявленной проверки, а не криптографическая подпись рецензента. Контрольная сумма связывает её с байтами файлов, но не доказывает личность, качество рецензии и отсутствие всех возможных дефектов.

Digest локального примера — SHA-256 потока: имена из `files` сортируются в ASCII-порядке; для каждого добавляются UTF-8 имя, NUL, десятичная длина файла в байтах, NUL, исходные байты, NUL. Сам `project.json` в digest не входит, поэтому его сведения отдельно проверяются вручную. Команда `--digest <slug>` считает сумму, ничего не изменяя.

Для внешнего комплекта локально хранятся только `README.md` и `project.json`. Поле `external` задаёт `repository` (публичный GitHub HTTPS), точный `commit`, `entrypoint`, `manifest`, `manifest_sha256`. Внешняя версия не подменяется плавающей веткой `main`. Указатель без сети доказывает только корректность своего формата. `review: null` здесь означает, что локальная карточка не выдаёт новую рецензию исходного комплекта.

Текущая внешняя проверка поддерживает точный состав Constitution.my 1.2: манифест и 22 перечисленных в нём файла. Для внешнего комплекта другой формы сначала явно расширяют проверку и тесты. Это не ограничивает число обычных локальных проектов из четырёх Markdown-файлов.

## Что проверяют команды

```sh
node scripts/validate.mjs
node scripts/test.mjs
node scripts/validate.mjs --remote
```

Первая команда читает локальную структуру, паспорта, разрешённые файлы и Markdown-ссылки; проверяет состояния и маркеры незаполненных авторских полей, обнаруживает некоторые признаки приватных путей и секретов. Поля будущего ответа подрядчика могут оставаться незаполненными. Вторая выполняет положительные и отрицательные тесты на временных синтетических папках, не меняя комплекты. Обе работают без установки пакетов, сети и изменения документов.

Третья дополнительно обращается без авторизации к закреплённому внешнему комплекту: сверяет манифест, дерево и байты файлов. Проверяет именно указанный commit, не текущий сайт и не обязательное совпадение с текущей `main`. Сетевая ошибка означает неполученное подтверждение, а не неверное содержание. Команды запускает человек; расписания и CI-процессы здесь не установлены.

Ни один скрипт не заменяет предметную проверку всех работ и ссылок W/R/C/OP, измерение полного корпуса, проверку прав и персональных данных, оценку справедливости требований или человеческую приёмку. Поиск нескольких признаков секретов не является исчерпывающей защитой от утечек. Перед публикацией всегда просматривают точный diff и список файлов. Внешние ответы подрядчиков в этот репозиторий автоматически не загружаются.

## После публикации

Проверить доступность публичного README, переход к проекту, закреплённые ссылки и вид документа на обычной и узкой ширине. Сопоставить публичный commit и файлы с проверенной локальной версией. Локальные тесты, публикация GitHub и проверка работающего продукта — разные результаты; последнюю этот репозиторий не выполняет.
